01 · Project overview

A practical product built around a real family need

Wordy is a private, phone-friendly vocabulary learning application for my family. It combines shared vocabulary decks with separate learner progress and multiple practice modes.

It was also my first independent experiment in directing AI-assisted product development: translating an informal need into explicit requirements, an evolving data model, a deployed application, and a set of product boundaries.

AI implementation disclosure

I owned the product vision, architectural direction, requirements, validation, and release decisions. AI coding agents generated and modified the implementation under my direction.

02 · The problem / motivation

Moving vocabulary practice beyond paper

Learning new languages with my kids often started with writing unfamiliar words on paper. I wanted an additional way to collect those words and practice them from a phone or browser.

The central design challenge was shared content with personal learning state: the family should be able to use the same vocabulary decks, while each learner needed independent progress. The project also gave me a concrete way to test whether an AI coding assistant could turn that need into a real, deployed product under clear human direction.

03 · My role

Product ownership and architectural direction

I framed the problem, defined requirements and delivery milestones, directed architectural choices, reviewed generated behavior, tested important journeys, and prioritized corrections.

My responsibility covered the product and solution direction, including deployment, data design, experience, and proportionate security decisions. The implementation code itself was generated and modified by AI coding agents.

04 · Product vision and scope

One shared learning space, distinct learner journeys

The product was intentionally scoped as a private family application rather than a public learning platform.

Shared vocabulary

Family members use common decks and cards instead of maintaining duplicate word lists.

Individual progress

Review state, activity, streaks, and achievements remain associated with each learner.

Multiple learning modes

Flashcards, multiple-choice questions, and typing practice support different ways to review.

Focused authoring

Decks support manual card entry and tab-separated bulk import.

05 · Architecture

A focused full-stack application

Wordy uses one Next.js application for the React interface and API route handlers, Prisma for data access, PostgreSQL on Neon for persistence, and Vercel for hosting.

06 · Key architectural decisions

Decisions shaped by product context

The design evolved as the application moved from local validation to family use on the web. These decisions were not all fixed at the beginning.

DECISION 01

Shared content, individual learner progress

Problem

The family needed common vocabulary decks without combining each learner's progress.

Decision

Keep decks and cards shared, while associating review data with an individual learner and card.

Rationale

Shared content avoids duplicate maintenance; learner-specific state preserves an accurate personal journey.

Tradeoff

Adding profiles required coordinated changes across the database, API, and interface.

Learning

Identity and ownership affect the whole system, even in a small private application. Existing progress was preserved under a starter profile during the migration.

DECISION 02

Current ReviewState and append-only ReviewEvent history

Problem

Study sessions need fast access to current review state, while progress features need historical activity.

Decision

Separate the current level and next review from an append-only history of learning activity.

Rationale

The split supports efficient study flows and historical questions such as streaks, achievements, and progress by mode.

Tradeoff

The current-state and historical representations must be kept consistent.

Learning

Operational state and historical evidence answer different questions and benefit from distinct models.

DECISION 03

From local SQLite to Neon PostgreSQL and Vercel

Problem

The local prototype's storage and runtime no longer matched a web-deployed family application.

Decision

Evolve from SQLite to managed PostgreSQL on Neon, deploy on Vercel, and apply Prisma migrations.

Rationale

The managed services fit the application's new operating context without introducing a larger hosting architecture.

Tradeoff

Deployment added migration and hosted-service considerations that were unnecessary during local validation.

Learning

Infrastructure should evolve with the product context. A briefly explored Docker route was discarded rather than preserved for its own sake.

DECISION 04

Lightweight family access

Problem

An internet-accessible family tool needed access controls proportionate to its private household use.

Decision

Use a lightweight family-access model instead of full individual account authentication.

Rationale

The approach matches the limited audience and avoids account infrastructure beyond the product's intended scope.

Tradeoff

It is not suitable as authentication for a public, multi-tenant product.

Learning

Security decisions need to be explicit about context and limits; proportionate does not mean universally sufficient.

07 · Challenges and iterations

The useful design emerged through refinement

Iteration went beyond adding functionality. Profile selection was corrected to survive refresh and locking, mobile swipe behavior was refined, and progress summaries were simplified after an overly comparison-heavy version.

The move to profiles required a cross-cutting migration while preserving existing progress. When the application became internet-accessible, access-control and input-handling protections were also strengthened. These changes illustrate an architecture responding to observed product needs rather than appearing fully formed at the start.

08 · Validation

Targeted evidence, with stated limits

The existing repository review reports 26 commits from February 5 to March 17, 2026, and ten passing focused regression tests: six for profile selection and persistence, and four for access and configuration behavior.

These figures describe targeted verification, not comprehensive automated coverage. They should be rechecked against the private application repository before being treated as current.

09 · Outcome

A deployed family product and a reusable way of working

Product outcome

A web-based, phone-friendly learning application with shared decks, individual progress, and several practice modes.

Architecture outcome

A full-stack design that evolved from local validation to managed web deployment while preserving existing use.

Wordy remains private because it contains family learning information. There is intentionally no public live demo or repository link.

10 · Lessons learned

Direction, inspection, and iteration remain human responsibilities

Wordy taught me to translate a personal need into explicit product boundaries, evolve a data model without abandoning existing usage, and treat AI-generated output as something to inspect and refine.

It also reinforced that architecture is not a one-time blueprint. The data model, hosting, access, and user experience all changed as the product moved from idea to real family use.

11 · What I would explore next

Strengthen validation in proportion to future scope

For continued private family use, the next useful exploration would be broader automated coverage around learning flows, progress calculations, and migration behavior, alongside ongoing usability refinement.

If the product context ever expanded beyond a private household, individually authenticated accounts and a corresponding security review would become architectural prerequisites—not incremental polish.
