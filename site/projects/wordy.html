Project 01 · AI-directed product architecture · February–March 2026

Wordy

A family learning need became a deployed, phone-friendly vocabulary application—and my first experiment directing AI-generated software.

Product: Private family learning application · My role: AI Product & Solutions Architect · Delivery: AI-generated implementation under my direction

The family problem

Learning new languages with my kids often started with writing unfamiliar words on paper. I wanted an additional way to collect those words and practice them from a phone or browser. The family needed to share vocabulary decks while keeping each learner's progress separate. I was also curious whether I could direct an AI coding assistant to turn that informal need into a real, deployed product.

My contribution and AI credit

I framed the problem, defined requirements and delivery milestones, directed architectural choices, reviewed generated behavior, tested important journeys and prioritized corrections. AI coding agents generated the source implementation; I did not manually author the application code. My responsibility was the product and solution direction, including deployment, data design, experience and proportionate security decisions.

What the product does

Wordy lets family members share vocabulary decks with independent learning progress. Learners can use flashcards, multiple-choice questions and typing practice. Deck creation supports manual card entry and tab-separated bulk import. A simplified level-based spaced-repetition model schedules reviews; progress summaries, streaks and achievements provide feedback. It is an application used within my family, not a public commercial learning platform.

Architecture at a glance

Interface and API: Next.js 16, React 19, TypeScript, App Router
Data access: Prisma ORM
Database: PostgreSQL on Neon
Hosting: Vercel
Design: One full-stack application with shared decks and learner-specific review data

Decision: separate shared content from personal progress

The family should not maintain duplicate copies of the same words, but each person needs their own learning history. I directed the model toward shared decks and cards with review data associated with an individual learner and card. Introducing profiles required a cross-cutting migration across the database, API and interface; existing progress was preserved under a starter profile.

Decision: distinguish where a learner is from how they got there

The data model separates ReviewState, which represents the current level and next review for one learner and card, from append-only ReviewEvent history, which records learning activity over time. This distinction supports efficient study sessions and historical questions such as streaks, achievements and progress by learning mode. The accepted tradeoff is that the two representations must be kept consistent.

Decision: evolve the deployment with the product

Early validation used local SQLite. When the application moved to the web, the architecture evolved to Vercel with managed PostgreSQL on Neon and Prisma migrations. A briefly explored Docker route was discarded. This was a practical example of changing infrastructure when the product's operating context changed, rather than defending the prototype's initial choices.

Usability, security and iteration

Iteration went beyond adding functionality: mobile swipe behavior was refined, profile selection was fixed to survive refresh and locking, and progress summaries were simplified after an overly comparison-heavy version. Because the family tool became internet-accessible, access control and input-handling protections were also strengthened. The lightweight family-access model matches a private household use case; it is not a substitute for individually authenticated accounts in a public multi-tenant product.

Evidence and limits

The Codex repository review reports 26 commits from February 5 to March 17, 2026, and ten passing focused regression tests: six for profile selection/persistence and four for access and configuration behavior. This is targeted verification, not comprehensive automated coverage. A public live demo is intentionally not linked because Wordy contains private family learning information.

What I took into my next project

Wordy taught me to translate a personal need into explicit product boundaries, evolve a data model without abandoning existing usage and treat AI-generated output as something to inspect and refine. With BoomArena, I took that AI-directed delivery approach into a different problem: real-time multiplayer synchronization and server-authoritative state.
